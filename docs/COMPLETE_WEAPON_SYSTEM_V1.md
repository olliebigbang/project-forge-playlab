# 通用武器系统 V1

更新：2026-08-30。范围是本地原型的完整玩法循环，不是线上发行版本。

后续主战场机制执行、逐轴验证及真实渲染审核见 [主战场机制执行 V1](MAIN_ARENA_MECHANISM_EXECUTION_V1.md)。本文下方 85 项测试及“未打开人工试玩窗口”记录属于先前的武器库/系统阶段，不代表后续试玩已经全部完成。

## 玩家现在走的流程

描述一个物品（可以附草图）→ AI 判断身份与结构 → 本地机制轴校验 → 生成像素物品 → 完整入库 → 装备打三战 → 结算 → 保留原武器、换武器或描述新物品。

- 工坊增加「打开我的武器库 / 三战关卡」。物品机制卡增加「保存并打开武器库」。进入正式关卡前必须保存成功。
- 枪械和普通物品在同一个武器库展示。上次使用的武器排在前面并有标记。
- 普通物品外形确认仍然只问“画得像不像”，不问握法、攻击动作或机制参数。后台奖励不向玩家提出机制确认问题。
- 三战仍使用已经验收的离线敌人蓝图、现有正式像素敌人与背景。战斗不等待在线 AI。
- 原来的枪械图片缓存继续兼容；缺少完整结构资料的旧普通物品图片不会被猜测重建成武器。

## 保存的是武器，不只是一张图

`WeaponLibraryStore` 保存在 Godot 的 `user://playlab/weapon_library/v1`：

| 内容 | 保存与恢复规则 |
| --- | --- |
| 图片 | 原始透明像素图、画布大小和不透明边界 |
| 握持位置 | 主握点、副握点、尖端、枪口、牵引起点、旋转点、后接触点及朝向信息 |
| 结构动画 | 分件、遮罩、曲线路径和绑定声明；恢复时按最终朝向重新绑定，不重复翻转 |
| 机制 | 完整蓝图、AI 声明、通用 affordance profile、射击最终参数矩阵 |
| 接受依据 | 视觉来源、已有检查结果、身份；不保存 API 密钥 |

每件武器先写临时目录，内容和图片哈希一致后才发布完整包。相同内容不会反复新增包。读取时检查哈希、机制和动画一致性；检查失败的条目单独跳过，不替换为默认加特林。

机制数据使用不允许对象反序列化的 Variant 数据格式，保留向量和整数类型。重新编译后与存档不一致会拒绝加载，不默默重置为当前默认值。编译器升级后的存档迁移不在本版范围内。

装备、奖励和最近一局结果使用独立完整快照。最新快照损坏时可回读较早完整快照。武器包和快照没有自动删除；本版不提供存档清理界面。

## 后台奖励如何决定

奖励不再补“缺一把冲锋枪”。系统统计现有武器的实际机制能力：

| 能力 | 来自什么 |
| --- | --- |
| 控制 | 硬直、缠绕、钩回等机制 |
| 防御 | 大接触面、展开结构、作用场 |
| 范围 | 接触面积、展开范围、散射覆盖 |
| 距离 | 主体长度、软线、延伸结构、射击或喷流距离 |
| 破甲 | 尖端、接触特征或编译后的穿透参数 |
| 轻快 | 重量分布、出手代价和移动能力 |

一件物品可以覆盖多个能力。修改名称不改变能力归类。AI 候选选择器只建议物品身份，不能直接指定伤害；正式解析器和机制编译器必须独立确认目标能力，再申请图片。

- 开始一局时才尝试后台造物；只浏览武器库不会调用付费生成。
- 六种能力都已覆盖，或已有待领取奖励时，不再发起额外生成。
- 每轮最多两个候选、累计三次视觉请求。请求数包括可能命中的缓存，因此这是保守的调用上限，并非精确美元预算。
- 未通过的候选记录在本地，24 小时内避免重复；记录最多保留 32 项。
- 图片、结构和机制必须通过检查且完整保存，才进入待奖励状态。
- 未通关不解锁；通关解锁后不会自动替换当前装备。奖励可留在武器库，下次启动继续选择。
- 旧枪械图片缓存同样遵守待奖励锁定，不能绕过完整武器库提前领取。
- 关闭场景会取消仍在进行的后台任务；已完整保存的待奖励继续保留。未完成请求不是跨进程可恢复任务，也不能保证取消后供应商未计费。

## 失败时怎么处理

识别失败、能力不符、图像/结构检查失败、保存失败都有明确停止点，不套用固定物品补成功。缺少密钥或在线服务不可用时，已有武器和离线三战仍可使用。

现在仍不支持把坦克编译成可驾驶载具，或把生物变成独立角色。此类输入会被明确拒绝，而不是伪装成普通棍棒。

## 自动验证

运行：

```powershell
.\scripts\test_complete_weapon_system.ps1
```

该入口清除子进程中的在线生成凭证，不读取 `.env`；使用隔离测试存档、隐藏的无界面 Godot 进程。结束后恢复原进程环境。日志和汇总保存在 `.tools/system-tests/<run-id>`。

覆盖：六种结构完整存取、握点和像素绑定不变、幂等入库、损坏文件隔离、未写完包不可见、结算快照恢复、奖励锁定/解锁/重开、普通物品武器库到三战结算、AI 路由、能力先验检查、重试上限、取消、现有敌人机制与武器交互、射击运行时及页面布局。

这些是离线契约与运行时测试。生成服务测试明确使用模拟提供者，不能作为真实在线 AI 理解率或新图片质量的证明；六结构存取测试也不声称创造了六件新美术资产。

本轮统一回归：85 项通过，0 项失败（Godot 8 组共 77 项，候选桥接器 Python 8 项）。Godot 在当前受限环境打印了系统证书库警告；这些测试均不访问在线生成接口，没有把该警告算作 API 验证成功。

最终日志目录：`.tools/system-tests/839da99a2e7c4e47874e658871ffb746/`，包含各组标准输出、错误输出、Godot 日志与 `summary.json`。目录仅为本地证据，不入版本库。

本轮按要求没有打开人工试玩窗口，没有调用付费 AI，没有生成新美术。已有的通用图像检查主要证明结构和动作可读性，不等同于所有物品均经过独立视觉身份审核。本版也不包含账号、云存档、服务器队列、计费或发布打包。

## 主要代码入口

- `scripts/combat_feel/weapon_library_store.gd`：完整包与会话存档。
- `scripts/combat_feel/player_weapon_armory.gd`：新库、旧枪械缓存、装备与奖励。
- `scripts/combat_feel/weapon_capability_catalog.gd`：名称无关的能力标签。
- `scripts/combat_feel/weapon_entry_factory.gd`：生成结果到完整机制武器的检查。
- `scripts/services/general_weapon_generation_service.gd`：通用/枪械路由和视觉请求状态机。
- `scripts/combat_feel/automatic_armory_director.gd`：能力缺口、候选和请求预算。
- `scripts/open_identity_spike.gd`、`scripts/enemy_attack/automatic_level_loop.gd`：工坊、武器库、装备、关卡与结算入口。
